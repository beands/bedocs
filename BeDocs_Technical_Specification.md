**Версия документа:** 1.0  
**Дата:** 9 августа 2026 года  
**Заказчик и владелец продукта:** BeandsMedia

**Проверенная исходная версия:** Blume 1.4.1

## 1. Общая концепция

BeDocs — самостоятельная русскоязычная платформа для создания технической документации, баз знаний, API-справочников и AI-ready порталов из Markdown/MDX. Продукт создаётся на основе Blume, сохраняет его основные возможности и совместимость с обновлениями upstream, но получает собственное название, CLI, конфигурацию, документацию, фирменную тему и русскую локализацию.

BeDocs должен подходить для:

- публичной документации продуктов;
- внутренних баз знаний компаний;
- OpenAPI/AsyncAPI-справочников;
- документации для разработчиков и пользователей;
- каталогов инструкций, Skills и промтов;
- подключения Codex, Cursor, Hermes Agent и других AI-агентов через `llms.txt`, Markdown и MCP;
- самостоятельного размещения на VPS, в Docker и на статических хостингах.

Основной принцип разработки: **локализация и брендинг должны быть отделены от ядра**, чтобы обновления исходного Blume можно было переносить без полного ручного слияния проекта.

## 2. Цели проекта

### 2.1. Основные цели

1. Создать полноценный русскоязычный форк Blume под названием BeDocs.
2. Сделать русский язык основным для интерфейса, CLI, шаблонов и документации.
3. Сохранить английский язык как дополнительную локаль.
4. Выпустить собственный npm-пакет и CLI-команду `bedocs`.
5. Обеспечить совместимость с Markdown, MDX, Astro, OpenAPI, поиском, Ask AI, MCP и экспортом.
6. Добавить шаблоны документации для проектов BeandsMedia.
7. Настроить безопасную и воспроизводимую синхронизацию с Blume upstream.
8. Подготовить проект к публичному open-source-релизу и дальнейшему развитию.

### 2.2. Критерии успеха

- новый проект создаётся одной командой и запускается без ручной настройки Astro;
- весь стандартный интерфейс и CLI доступны на русском языке;
- проект успешно собирает статический сайт и серверную версию;
- обновления Blume можно переносить по документированному регламенту;
- пакет публикуется автоматически только после прохождения проверок;
- в пользовательской документации отсутствуют ссылки и команды, которые ошибочно устанавливают оригинальный пакет вместо BeDocs;
- лицензия и авторство исходного проекта соблюдены.

## 3. Границы проекта

### 3.1. Входит в первую публичную версию

- форк репозитория и настройка upstream;
- ребрендинг Blume в BeDocs на всех пользовательских поверхностях;
- npm-пакет `@beands/bedocs` и CLI `bedocs`;
- `bedocs.config.ts` и генерируемая директория `.bedocs/`;
- русский и английский интерфейсы;
- русская документация и Quick Start;
- создание, запуск, сборка, проверка и диагностика проектов;
- Markdown/MDX и встроенные компоненты;
- локальный поиск с корректной обработкой русского текста;
- SEO, Open Graph, sitemap, RSS и `robots.txt`;
- OpenAPI/AsyncAPI-справочник;
- `llms.txt`, `llms-full.txt`, Markdown-копии страниц;
- Ask AI через OpenAI-compatible endpoint;
- read-only MCP-сервер;
- PDF/EPUB-экспорт, если функция сохраняется работоспособной из upstream;
- фирменная тема BeDocs;
- базовые шаблоны Synthix, Taskcraft CRM, BeandsBooker и универсальный шаблон;
- тесты, CI/CD, Changesets, выпуск npm и GitHub Release;
- регламент синхронизации с upstream.

### 3.2. Не входит в MVP

- визуальный WYSIWYG-редактор документации;
- облачная SaaS-панель с аккаунтами и оплатой;
- совместное редактирование в реальном времени;
- закрытая авторизация и управление ролями внутри статического сайта;
- собственная облачная поисковая инфраструктура;
- собственная LLM или векторная база;
- мобильное приложение;
- гарантированная обратная совместимость с неофициальными внутренними API Blume.

Эти функции могут быть добавлены после стабилизации BeDocs 1.0.

## 4. Исходная техническая база

Исходный Blume на момент подготовки ТЗ имеет следующую архитектуру:

- monorepo на Bun Workspaces и Turborepo;
- `packages/blume` — публикуемый пакет;
- `apps/docs` — собственная документация, собранная самим движком;
- Astro 7 и Vite;
- TypeScript, React 19 для интерактивных islands;
- Tailwind CSS 4;
- Zod для схем конфигурации;
- Bun Test;
- Changesets для версий и релизов;
- локальный поиск Orama и адаптеры других провайдеров;
- Scalar для OpenAPI/AsyncAPI;
- Model Context Protocol SDK;
- минимальная версия Node.js — 22.12;
- рабочая версия Bun в upstream — 1.3.14.

Разработчик обязан сохранить модульное деление ядра: `cli`, `core`, `astro`, `components`, `markdown`, `theme`, `search`, `og`, `seo`, `deploy`, `openapi`, `ai`, `registry`, `runtime`.

## 6. Стратегия форка и синхронизации

### 6.1. Репозитории и remotes

Рекомендуемое имя репозитория: `beandsmedia/bedocs`.

Обязательные Git remotes:

```text
origin    git@github.com:beandsmedia/bedocs.git
upstream  https://github.com/haydenbleasel/blume.git
```

Основные ветки:

- `main` — стабильный код BeDocs;
- `develop` — интеграционная ветка, если команда использует Git Flow;
- `upstream-sync/<version>` — временная ветка синхронизации;
- `feature/*`, `fix/*`, `release/*` — рабочие ветки.

### 6.2. Правила минимизации конфликтов

1. Не выполнять массовое переименование внутренних типов, функций и комментариев только ради замены слова Blume.
2. Все пользовательские названия вынести в единый модуль `product-meta.ts` или аналогичный.
3. Все UI-строки хранить в словарях локализации.
4. Пути `.bedocs`, имя конфига и package specifier хранить в централизованных константах.
5. Фирменную тему реализовать отдельным слоем токенов и компонентов.
6. Каждый BeDocs-specific патч сопровождать тестом и пометкой в `UPSTREAM.md`.

### 6.3. Регламент синхронизации

Для каждого нового релиза Blume:

1. Создать issue «Sync Blume X.Y.Z».
2. Проверить changelog, breaking changes, зависимости и лицензию.
3. Создать ветку `upstream-sync/x.y.z`.
4. Выполнить слияние или rebase согласно принятой стратегии репозитория.
5. Разрешить конфликты, не удаляя BeDocs-specific адаптеры.
6. Запустить полный CI, сборку документации и smoke-тест CLI.
7. Обновить `UPSTREAM.md` и матрицу совместимости.
8. Открыть отдельный PR с перечнем перенесённых и отклонённых изменений.
9. Выпускать новую версию BeDocs только после ручной проверки русской локализации.

Автоматический workflow может создавать PR синхронизации, но не имеет права автоматически сливать его в `main`.

export const productMeta = {

Если найден только `blume.config.ts`, BeDocs должен:

- временно загрузить его;
- вывести понятное предупреждение на русском;
- предложить команду миграции или автоматическое переименование;
- не изменять файл без подтверждения пользователя;
- удалить поддержку legacy-имени только в следующей major-версии после объявления deprecation.

### BR-04. Проверка остаточного брендинга

Добавить автоматическую проверку пользовательских поверхностей на случайные упоминания:

- старой CLI-команды;
- старого package specifier;
- `github.com/beands/bedocs` в создаваемых шаблонах;
- `.blume/` в инструкциях, ошибках и выводе CLI.

Упоминания Blume разрешены в лицензии, NOTICE, истории проекта, upstream-документации и технических комментариях о совместимости.

## 9. Локализация

### I18N-01. Поддерживаемые языки

- `ru` — основной язык и локаль по умолчанию;
- `en` — дополнительный язык;
- архитектура должна позволять добавлять новые локали без изменения компонентов.

### I18N-02. Обязательные зоны перевода

Перевести:

- навигацию сайта;
- поиск и сообщения об отсутствии результатов;
- кнопки копирования, экспорта, переключения темы и языка;
- Ask AI и все его состояния;
- пагинацию, оглавление и хлебные крошки;
- страницу 404;
- OpenAPI-интерфейс в пределах возможностей Scalar;
- системные сообщения CLI;
- вопросы интерактивного `bedocs init`;
- ошибки, предупреждения и подсказки `doctor`;
- стартовые шаблоны;
- README, документацию, FAQ и troubleshooting;
- skills, создаваемые или поставляемые BeDocs.

### I18N-03. Правила перевода

- Использовать естественный технический русский язык, а не дословный машинный перевод.
- Команды, имена пакетов, API-поля и код не переводить.
- Для терминов Markdown, MDX, OpenAPI, MCP и CLI использовать единый глоссарий.
- Букву `ё` сохранять в интерфейсных текстах, но поиск должен находить варианты и с `е`, и с `ё`.
- Избегать смешения «Вы» и «ты»; рекомендуемый стиль документации — нейтральный безличный.
- Все строки должны поддерживать подстановки и plural rules через `Intl.PluralRules` или эквивалентный механизм.

### I18N-04. Контроль полноты

CI должен завершаться ошибкой при:

- отсутствии обязательного ключа в `ru`;
- наличии лишнего ключа, не соответствующего базовой схеме;
- пустом переводе;
- ошибочной интерполяции переменных;
- появлении новой UI-строки непосредственно в компоненте вместо словаря.

### I18N-05. SEO локалей

Для многоязычного сайта обеспечить:

- корректные `lang` и `hreflang`;
- локализованные title/description;
- canonical URL;
- отдельные sitemap-записи;
- отсутствие дублей между `/` и `/ru/` согласно выбранной стратегии маршрутов.

## 10. CLI BeDocs

### CLI-01. Команды

Обязательные команды:

| Команда | Назначение |
|---|---|
| `bedocs init [dir]` | создать новый проект |
| `bedocs dev` | запустить локальный сервер |
| `bedocs build` | собрать production-версию |
| `bedocs preview` | открыть локальный preview сборки |
| `bedocs add <item>` | добавить компонент из registry |
| `bedocs sync` | обновить удалённые источники контента |
| `bedocs eject` | выгрузить генерируемый Astro-проект |
| `bedocs check` | выполнить типизацию и Astro Check |
| `bedocs validate` | проверить ссылки, якоря и ресурсы |
| `bedocs doctor` | диагностировать окружение и конфиг |
| `bedocs migrate blume` | перенести проект Blume в BeDocs |
| `bedocs --version` | показать версии BeDocs и upstream base |
| `bedocs --help` | показать русскую справку |

Все существующие upstream-команды, перенесённые в BeDocs, должны сохранять поведение, если оно не противоречит данному ТЗ.

### CLI-02. `bedocs init`

Интерактивный мастер должен запрашивать:

- папку проекта;
- название и описание сайта;
- язык по умолчанию;
- тип шаблона;
- пакетный менеджер;
- режим сборки: static или server;
- необходимость поиска, Ask AI и OpenAPI;
- инициализацию Git.

Поддержать неинтерактивный режим для CI:

```bash
bedocs init my-docs --template synthix --locale ru --package-manager bun --yes
```

### CLI-03. Безопасность файловых операций

- не перезаписывать существующие файлы без подтверждения или `--force`;
- перед миграцией показывать список изменений;
- поддержать `--dry-run` для миграции;
- прерывать операцию при невалидном конфиге;
- выводить понятные пути и рекомендации по исправлению;
- не печатать секреты и токены в логах.

### CLI-04. Коды выхода

- `0` — успешное выполнение;
- `1` — ошибка пользователя или проверки;
- `2` — ошибка конфигурации;
- `3` — ошибка окружения или зависимостей;
- ненулевой код обязателен при ошибках `check`, `validate`, `doctor --strict` и `build`.

## 11. Конфигурация проекта

### CFG-01. Основной файл

Использовать `bedocs.config.ts` с типобезопасной функцией `defineConfig` из `@beands/bedocs`.

Пример:

```ts
import { defineConfig } from "@beands/bedocs";

export default defineConfig({
  i18n: {
    defaultLocale: "ru",
    locales: ["ru", "en"],
  },
  logo: {
    text: "BeDocs",
  },
  site: {
    description: "Документация проекта",
    title: "Моя документация",
    url: "https://docs.example.ru",
  },
});
```

### CFG-02. Валидация

- строгая схема конфигурации;
- понятные русские сообщения с точным путём ошибочного поля;
- автодополнение TypeScript;
- отказ от запуска при критической ошибке;
- предупреждения для deprecated-полей;
- миграция конфигурации между major-версиями.

### CFG-03. Секреты

API-ключи запрещено хранить в `bedocs.config.ts`. Конфигурация должна ссылаться только на имена переменных окружения или server-side provider.

Рекомендуемые переменные:

```text
BEDOCS_AI_BASE_URL=
BEDOCS_AI_API_KEY=
BEDOCS_AI_MODEL=
BEDOCS_AI_MAX_REQUESTS_PER_MINUTE=20
BEDOCS_SITE_URL=
GITHUB_TOKEN=
```

`BEDOCS_AI_API_KEY` не должен попадать в client bundle, HTML, sourcemap, логи или генерируемые файлы документации.

## 12. Контент и компоненты

### CNT-01. Форматы

Поддержать:

- `.md`;
- `.mdx`;
- frontmatter;
- `meta.ts` для групп и порядка страниц;
- пользовательские типы контента и расширяемую валидацию frontmatter;
- локальные и удалённые источники, поддержанные upstream;
- пользовательские страницы Astro.

### CNT-02. Встроенные компоненты

Сохранить и документировать компоненты: карточки, колонки, шаги, вкладки, аккордеоны, badges, code groups, frames, file tree, type table, diff, Mermaid, математические формулы и live previews — в объёме, доступном в исходной версии.

Для каждого компонента подготовить:

- русское описание;
- пример кода;
- визуальный пример;
- ограничения;
- требования доступности.

### CNT-03. Источники контента

Сохранить поддержку:

- локальной файловой системы;
- удалённого MDX;
- GitHub Releases;
- Notion;
- Sanity;
- пользовательского адаптера.

Токены внешних систем должны считываться только на сервере или во время сборки.

### CNT-04. Черновики и приватные страницы

- страницы с `draft: true` не публиковать в production;
- `hidden` не должен автоматически означать приватность;
- контент, исключённый из AI, не должен попадать в `llms.txt`, MCP и Ask AI;
- документация обязана явно объяснять, что статическая сборка не является системой контроля доступа.

## 13. Поиск

### SRCH-01. Базовый поиск

По умолчанию использовать локальный поиск Orama без обязательного внешнего сервиса. Сохранить поддерживаемые upstream-адаптеры, включая Pagefind, FlexSearch, Algolia, Typesense, Orama Cloud и другие, присутствующие в проверенной версии.

### SRCH-02. Русский язык

Добавить слой нормализации:

- Unicode normalization;
- приведение к нижнему регистру с учётом locale;
- эквивалентность `е` и `ё`;
- корректная токенизация кириллицы;
- поиск по заголовку, описанию, тексту, тегам и коду с разными весами;
- отсутствие потери латинских имён API и команд.

Морфологический поиск допускается реализовать отдельным адаптером. Он не должен ухудшать точное совпадение по коду, идентификаторам и названиям пакетов.

### SRCH-03. Проверочные запросы

Автотесты должны подтверждать, что:

- «настройка» находит страницу с соответствующим словом;
- запрос с `е` находит документ с `ё` и наоборот;
- `bedocs build` находится как точное техническое выражение;
- поиск не показывает draft и исключённые страницы;
- язык интерфейса состояния «ничего не найдено» соответствует активной локали.

## 14. AI-ready функции

### AI-01. `llms.txt` и Markdown

Сохранить генерацию:

- `llms.txt`;
- `llms-full.txt`;
- сырой Markdown-копии страницы;
- функции «Копировать как Markdown»;
- ссылки открытия документа в поддерживаемом AI-клиенте, если она безопасна и настроена.

Из AI-выдачи исключать draft, `ai.exclude: true`, служебные страницы и любой контент, запрещённый конфигурацией.

### AI-02. Ask AI

Ask AI должен работать через настраиваемый OpenAI-compatible endpoint. Интеграция не должна быть жёстко привязана к одному провайдеру или модели.

Обязательные возможности:

- server-side хранение ключа;
- выбор модели через переменную окружения или server config;
- streaming-ответ;
- ответы только на основе разрешённой документации;
- ссылки на страницы-источники;
- сообщение о недостатке данных вместо выдуманного ответа;
- ограничение размера контекста;
- timeout, retry с backoff и отмена запроса;
- rate limit по IP/сессии;
- максимальная длина вопроса;
- безопасное отображение Markdown;
- отключение функции без изменения контента сайта.

### AI-03. MCP

Предоставить read-only MCP с инструментами поиска и чтения разрешённой документации. MCP не должен:

- изменять файлы;
- выполнять команды;
- читать `.env`, Git-метаданные и произвольные пути;
- возвращать draft или исключённые материалы;
- открывать SSRF-доступ к произвольным URL.

Для MCP определить версию протокола, ограничения запросов, формат ошибок и health-check.

### AI-04. Защита от prompt injection

- контент документации считать недоверенными данными;
- отделять системные инструкции от содержимого страниц;
- не выполнять инструкции из индексируемого контента;
- очищать опасный HTML;
- не передавать модели секреты, cookies и внутренние заголовки;
- документировать ограничения и модель угроз.

## 20. Безопасность

### SEC-01. Supply chain

- lockfile обязателен;
- установка в CI только с frozen lockfile;
- Dependabot или Renovate;
- проверка известных уязвимостей зависимостей;

- запрет публикации из локальной машины как штатного процесса;
- минимальные GitHub Actions permissions;
- сторонние Actions фиксировать на безопасные версии или commit SHA согласно политике команды.

### SEC-02. Секреты

- `.env*` в `.gitignore`, кроме безопасного `.env.example`;
- secret scanning;
- тест, что ключи не попадают в `dist/`;
- маскирование чувствительных значений в логах;

### SEC-03. Web security

- безопасная обработка MDX и пользовательского HTML;
- защита от XSS;
- CSP-шаблон для server deployment;
- защита AI endpoint от CSRF/abuse в соответствии с выбранной схемой сессий;
- rate limiting;
- ограничение тела запроса;
- SSRF-защита для удалённых источников и OpenAPI URL;
- корректные security headers в Node/Docker deployment guide.

### SEC-04. Disclosure

Добавить `SECURITY.md` с поддерживаемыми версиями, способом приватного сообщения об уязвимости и ожидаемыми сроками ответа.

## 21. Тестирование

### 21.1. Уровни тестов

1. **Unit:** схемы, i18n, нормализация поиска, CLI helpers, AI filters.
2. **Integration:** генерация `.bedocs`, загрузка конфига, content graph, OpenAPI, источники.
3. **CLI smoke:** все команды на чистом временном проекте.
4. **E2E:** init → dev/build → preview → search → locale switch → Ask AI mock.
5. **Visual regression:** основные страницы, обе темы и контрольные ширины.
6. **Accessibility:** axe и клавиатурные сценарии.
7. **Security:** XSS fixtures, path traversal, SSRF, secret leakage, rate limit.
8. **Migration:** Blume-проект преобразуется в BeDocs без потери контента.
9. **Upstream compatibility:** ключевые upstream-тесты проходят без модификации ожидаемого поведения.

### 21.2. Минимальные quality gates

- все тесты зелёные;
- typecheck без ошибок;
- lint/format без ошибок;
- сборка официальной документации успешна;
- проверка переводов успешна;
- coverage не ниже upstream-порога для затронутых файлов; ориентир — 98% lines/functions там, где upstream уже применяет этот порог;
- отсутствие high/critical уязвимостей без оформленного исключения;
- отсутствие critical/serious accessibility findings на ключевых страницах.

### 21.3. Обязательные сценарии приёмки

```bash
npx @beands/bedocs init demo --locale ru --yes
cd demo
bedocs doctor --strict
bedocs check
bedocs validate
bedocs build
bedocs preview
```

Проверка выполняется минимум с Bun и npm. Для pnpm/yarn допускается отдельная матрица CI.

| Плохой поиск по-русски | низкая полезность | нормализация, тестовый корпус, опциональная морфология |
| npm name занят | задержка релиза | использовать scope `@beands/bedocs`, проверить до разработки |
| Перевод Scalar ограничен | смешанный API UI | локализовать доступные элементы, ограничения документировать |
| Рост bundle size | ухудшение UX | performance budget и lazy loading |
| Скрытая несовместимость package managers | ошибки пользователей | CI-матрица и чистые smoke-проекты |

## 28. Критерии приёмки версии 1.0

Версия принимается, если одновременно выполнены условия:

1. Репозиторий публично или приватно доступен владельцу и имеет настроенный `upstream`.
2. MIT LICENSE сохранён, `NOTICE.md` заполнен.
3. Пакет устанавливается из npm и предоставляет бинарную команду `bedocs`.
4. `bedocs init` создаёт валидный русскоязычный проект.
5. `dev`, `build`, `preview`, `check`, `validate`, `doctor`, `add`, `sync`, `eject` работают согласно документации.
6. Конфигурация загружается из `bedocs.config.ts`; legacy-конфиг обрабатывается с предупреждением.
7. Генерируемый runtime находится в `.bedocs/` и может быть безопасно удалён и восстановлен.
8. Основной UI, CLI, ошибки и документация переведены на русский; английская локаль работоспособна.
9. Поиск корректно индексирует кириллицу и обрабатывает `е/ё`.
10. Draft и AI-excluded материалы отсутствуют в production search, `llms.txt`, Ask AI и MCP.
11. AI-ключ отсутствует в `dist/`, HTML, JS bundle и логах.
12. Ask AI имеет rate limit, timeout и ссылки на источники.
13. MCP работает только на чтение и не выходит за пределы разрешённого content graph.
14. OpenAPI/AsyncAPI demo собирается и отображается без критических ошибок.
15. Тема корректна в light/dark и на мобильных разрешениях.
16. Все обязательные тесты и CI checks проходят.
17. Официальная документация успешно собирается самим BeDocs.
18. Создан GitHub Release, changelog и воспроизводимая npm-публикация через OIDC.
19. Проведён пробный upstream sync и результат отражён в `UPSTREAM.md`.
20. Нет открытых P0-дефектов, critical/high уязвимостей и serious accessibility issues без утверждённого исключения.

## 29. Definition of Done для каждой задачи

Задача считается завершённой, когда:

- код реализован без неоправданного изменения upstream-ядра;
- добавлены или обновлены тесты;
- добавлен Changeset, если меняется пользовательское поведение;
- русская и английская документация обновлены;
- новые UI-строки добавлены в словари;
- выполнены lint, typecheck, tests и build;
- проверены безопасность и доступность затронутой функции;
- PR описывает влияние на upstream sync;
- нет секретов, временных файлов и сгенерированной `.bedocs/` в Git;
- критерии приёмки задачи подтверждены reviewer.

## 31. Рекомендуемый порядок первого запуска разработки

```bash
git clone <URL-форка> bedocs
cd bedocs
git remote add upstream https://github.com/haydenbleasel/blume.git
git fetch upstream --tags
bun install --frozen-lockfile
bun run check
bun run typecheck
bun run test
cd apps/docs
bun run build
```

После фиксации исходной зелёной сборки создать отдельный ADR с решениями по package name, runtime directory, legacy compatibility и стратегии upstream merge. Только после этого начинать ребрендинг.
